# UI Design Standard Skill V7.1

本 Skill 是 ECC V2 原型设计阶段（B2）的设计底线。它不固定审美风格或生产技术栈；B2 必须优先遵循 B1 Design Spec 与视觉调研证据。

---

## 设计上下文优先

- 优先使用 `.sdd/tmp/ui-design-spec.md` 中确认的设计方向、色彩、字体、间距、圆角、阴影、组件语言和信息密度。
- 如果 `.sdd/tmp/visual-research.md` 存在，原型必须参考其中列出的竞品截图 / URL / 视觉证据。
- 竞品只能用于借鉴结构、交互和视觉规律，禁止照搬品牌、Logo、真实商业文案和数据。
- 如果没有视觉上下文：
  - 桌面 Web 默认使用 Ant Design 风格基底
  - H5 页面默认使用 Ant Design Mobile 风格基底，并额外读取 `harness-core/skills/sdd-h5-product-design/SKILL.md`
  - 原生微信小程序默认使用微信原生组件 / WeUI / TDesign Miniprogram 风格基底，并额外读取 `harness-core/skills/sdd-wechat-miniprogram-product-design/SKILL.md`
  - 课程 / 讲解页默认使用清晰、克制、高对比的教学视觉基底

---

## 字阶策略

- 优先使用 B1 Design Spec 中确认的字体。
- 如果没有字体上下文：
  - 桌面 Web：系统 sans-serif + 组件库默认字体
  - H5 页面：系统 sans-serif，保证手机近距离阅读清晰
  - 原生微信小程序：系统 sans-serif，字号与触控目标遵循小程序近距离阅读和单手操作场景
  - 16:9 课件：标题与正文必须拉开字号层级，投屏可读
- 字阶必须按信息层级递减，避免所有文字平均用力。

---

## 圆角与密度

- 圆角、间距、阴影优先继承 Design Spec。
- 如果无明确上下文：
  - 业务型桌面 Web：核心组件圆角建议 6px-10px
  - H5 页面：卡片和按钮可适度放大圆角，但不得牺牲信息密度
- 数据密集场景允许高密度，但必须保持扫描路径清晰。
- AI / 数据 / 上下文感知类产品，至少展示 3 处真实产品差异化信息：推荐理由、推理片段、状态判断、趋势标签、置信度、上下文来源等。

---

## 布局效率

- 布局必须服务于用户任务，不为了装饰增加卡片、图标、渐变或无意义统计。
- 桌面 Web：优先清晰的信息区块、稳定导航、表格/列表/详情的扫描效率。
- H5 页面：优先单列、卡片、底部操作、明确返回路径；避免桌面表格直接搬到手机。具体规则以 `sdd-h5-product-design` 为准。
- 原生微信小程序：优先页面栈清晰、TabBar 稳定、胶囊按钮避让、安全区正确、授权/支付/订阅消息等微信能力入口明确。具体规则以 `sdd-wechat-miniprogram-product-design` 为准。
- 16:9 课件：每页只承载一个主要观点，图示和文字不能互相遮挡。

---

## 语言策略

- 所有显示文字必须全中文。
- 禁止英文占位符。
- 示例数据必须服务于当前业务，不得使用“数据1/数据2”。
- 没有真实数据时使用诚实 placeholder，不编造关键业务事实。

---

## 色彩与对比

- 优先使用 B1 Design Spec 中确认的色彩 token。
- 如果没有色彩上下文，使用默认业务系统配色：
  - Background：浅色中性背景
  - Text：高对比深色文本
  - Primary：单一主色
  - Border：低对比中性色
- 核心指标、主操作或当前任务状态必须有明确视觉锚点。
- 禁止无依据使用大面积紫色渐变、装饰性光斑、无意义高饱和背景。

---

## 反 AI slop（识别度优先）

反 slop 不是审美洁癖，是替产品保护识别度。服从 B1 Design Spec 是正向方式，下面的清单是反向兜底。

以下元素**默认规避**，唯一合法破例理由是「Design Spec / 品牌本身明确要求」：


| slop 元素                                   | 为什么                      | 改用                                    |
| ----------------------------------------- | ------------------------ | ------------------------------------- |
| 无依据紫色渐变                                   | "科技感"万能公式，撞遍 SaaS/AI 落地页 | Design Spec 的色 token 或单一主色            |
| emoji 当图标                                 | "不够专业就用 emoji 凑"的病       | 承载信息的图标，或干脆不放                         |
| 圆角卡片 + 左侧彩色 border accent                 | 烂大街的视觉噪音                 | 诚实的边界 / 分隔线                           |
| SVG 手画人物 / 人脸 / 实物                        | AI 画的人物五官错位、比例诡异         | 真实素材（如可用）或诚实 placeholder，不画烂 SVG      |
| 系统字体（Inter/Roboto/Arial/系统默认）当 display 标题 | 看不出"有设计"还是"demo 页"       | 有特点的 display 字型 + body 配对（缺上下文时按字阶策略） |


**真图诚实性测试**：放任何配图前先自问「去掉这张图，信息是否有损？」

- 装饰性、与内容无内在关联的图（Essay 配灵感图、设置页装饰 banner）→ **不要加**，加了就是 slop。
- 内容本身、有内在关联的图（产品实物、人物肖像、地点地图）→ **应该有**。

---

## 交互状态

所有关键交互组件必须至少覆盖：

1. 默认状态
2. Hover / Pressed 状态（桌面 Web）
3. Disabled 状态
4. Loading 状态（涉及请求）
5. Error / Empty 状态（涉及数据）

---

## 原型与生产前端边界

- 原型 HTML 用于设计验证，不是生产前端源码。
- 生产前端必须按阶段 C 批准的技术栈和工程规范重建；原型不得擅自决定生产框架。
- 原生微信小程序的生产前端必须按 `mobile/miniprogram/` 小程序工程重建，原型 HTML 不得当作 `.wxml/.wxss/.ts` 生产源码。
- 原型完成时必须给后续 Developer 留出：页面清单、组件清单、交互状态、Mock 数据结构、真实 API 位置。

---

## 验证清单

原型产出提交用户确认前，必须通过以下检查：

- 是否读取并使用 `.sdd/tmp/ui-design-spec.md`
- 如存在 `.sdd/tmp/visual-research.md`，是否真实参考截图 / URL / 视觉证据
- 所有显示文字是否全中文
- 是否无英文占位符和“数据1/数据2”
- 是否无明显重叠、裁切、溢出
- 桌面 Web 是否检查 1440×900
- H5 页面是否检查 390×844，并按 `sdd-h5-product-design` 检查头部、底部、安全区、触控目标和层级
- 原生微信小程序是否检查 375×812 或 390×844，并按 `sdd-wechat-miniprogram-product-design` 检查导航栏、胶囊避让、TabBar、安全区、授权/失败态和微信能力入口
- 关键交互是否有状态反馈
- 可点击 flow demo 是否能走通关键路径
- 是否明确原型代码不作为生产前端源码
