# 阶段 A：页面 → 功能 → 版本规划 → PRD

## 阶段 A 输入

进入阶段 A 前，必须已经完成阶段 R 的需求对齐、竞品调研与视觉证据沉淀。阶段 A 只负责把阶段 R 已确认的产品方向落成页面、功能、版本规划和 PRD 初稿。

如果发现系统要解决的问题、目标用户、使用场景或大致功能仍不清楚，停止阶段 A，返回阶段 R 补齐需求对齐。

## 固定产出

`docs/PRD.md`（持续迭代，本阶段结束时为初稿状态，阶段 C 补充定稿）。

PRD.md 包含：页面清单、主功能定义与分析、版本规划（Mission / Persona / V1·MVP / V2+）、业务规则、复杂链路、数据契约清单。如阶段 R 已识别 AI 功能，PRD.md 必须承接阶段 R 的 AI 参与位置、提示词/意图体系材料状态、默认配置和智能边界。

如果项目是原生微信小程序，PRD.md 还必须承接 `sdd-wechat-miniprogram-product-design` 的「微信小程序能力清单」，写明入口来源、登录/授权、TabBar、页面栈、微信开放能力、审核约束和拒绝授权后的降级策略。

**执行顺序（禁止跳步）**：先确定「有哪些页面」，再基于页面梳理「每个页面做什么功能」，最后才落到「分几版做、哪些数据规则」。

```
A1 页面梳理 → A2 主要功能定义与分析 → A3 版本规划
→ A4 关键功能实现思路 → A5 数据契约确认
→ 落盘 PRD.md → 总确认
```

## A1：页面梳理（必须先做）

基于阶段 R 已选方向，先与用户对齐**产品全貌的页面结构**：

1. **列出所有页面**（或关键视图），包括：
  - 页面名称（用户可理解的自然语言命名）
  - 页面类型（列表页 / 详情页 / 表单页 / 仪表盘 / 对话页 等）
  - 可见角色（谁能看到这个页面）
2. **页面跳转逻辑**：
  - 从哪来、到哪去
  - 主要入口（导航菜单 / 按钮跳转 / 链接）
3. **全局布局结构**（如涉及）：
  - 是否有统一侧边栏 / 顶部导航
  - 公共模块（用户信息、通知、搜索）分布在哪

**输出格式约束**：

````markdown
### 页面清单

| 序号 | 页面名称 | 页面类型 | 可见角色 | 入口来源 | 跳转去向 |
|------|---------|---------|---------|---------|---------|
| P01 | 登录页 | 表单页 | 未登录用户 | 直接访问 | 首页/仪表盘 |
| P02 | 仪表盘 | 仪表盘 | 管理员 | 侧边栏 | 详情页 |

### 页面跳转图

```text
登录页 → 仪表盘 → 详情页
  ↓
注册页
```
````

**门禁**：用户明确确认「页面清单和跳转逻辑」后，才能进入 A2。

---

## A2：主要功能定义与分析（在 A1 确认之后）

**基于 A1 的每个页面**，逐页定义其承载的功能。

### 输出格式约束

```markdown
### 页面：P02 仪表盘

#### 功能清单

| 功能编号 | 功能名称 | 一句话描述 | 用户可感知的完成标准 |
|---------|---------|-----------|-------------------|
| F-02-01 | 数据概览 | 展示核心指标卡片 | 用户进入页面即看到3-5个实时数据卡片 |
| F-02-02 | 趋势图表 | 展示近7天数据趋势 | 用户可选择时间范围，图表随之更新 |

#### 功能边界（做什么 / 不做什么）

| 功能编号 | 包含 | 不包含 |
|---------|------|--------|
| F-02-01 | 展示总用户数、订单数、收入 | 不展示明细列表、不支持导出 |
| F-02-02 | 折线图展示趋势 | 不支持对比多个维度、不支持下钻 |

#### 与其他页面的关联

- 点击数据卡片 → 跳转 P03 明细列表页（携带筛选参数）
- 点击趋势图数据点 → 弹出当日详情弹窗（不跳转新页面）
```

**执行规则**：

1. 按页面顺序逐个分析，不要跨页面混排，页面编号用P-{页面序号}，如P01
2. 每个功能必须有明确的「用户可感知的完成标准」（用户怎么知道这个功能有了）
3. 功能编号规则：`F-{页面序号}-{功能序号}`，如 `F-02-01`

**门禁**：用户确认「所有页面的功能清单和边界」无歧义后，才能进入 A3。

## A3：版本规划 — Roadmap（在 A2 确认之后）

在**页面结构和功能定义**清楚的前提下，划分：

- **V1 / MVP**：哪些页面、哪些功能、做到什么深度（与 A2 定义一致）
- **V2+**：哪些页面或功能延后、为什么（依赖、成本、风险、非核心）
- 写入 **Mission、Persona、关键业务逻辑 (Business Rules)**，与上述切分自洽

**输出格式约束**：

```markdown
### 版本规划

#### V1 / MVP

| 页面 | 包含功能 | 排除功能 | 理由 |
|------|---------|---------|------|
| P01 登录页 | F-01-01 账号密码登录 | F-01-02 第三方登录 | 第三方登录需要申请Key，阻塞MVP |
| P02 仪表盘 | F-02-01 数据概览 | F-02-02 趋势图表 | 图表库引入增加复杂度，V2再做 |

#### V2+

| 功能 | 预计版本 | 延后理由 |
|------|---------|---------|
| F-01-02 第三方登录 | V1.1 | 需要微信/钉钉开放平台审核 |
| F-02-02 趋势图表 | V1.2 | 需要引入图表库，当前MVP以表格展示替代 |
```

**规则**：版本划分必须能回答「为什么这一块在 MVP、那一块在 V2」——依据应是实现复杂度、依赖链、风险，而不是随意罗列。

**门禁**：用户确认版本规划与对功能的取舍无误后，才能进入 A4。

## A4：关键功能的实现思路（与页面/链路穿插完成）

对 PRD 中的主功能或子链路，必须与用户逐步对齐技术实现思路。

**适用范围**：只对「复杂业务链路」或「涉及关键技术选型的功能」做 A4 对齐（如 AI 召回、支付、实时通信、工作流编排）。普通 CRUD / 页面交互不需要单独写 A4。

**输出格式约束**：

````markdown
### 关键链路：召回链路（位于 P03 购物 Agent 对话页面）

- **触发场景**：用户在对话框输入问题后
- **实现思路**：关键词召回 / 向量召回 / 混合召回（与用户对齐选择）
- **关键技术选型**：若用向量，使用什么 Embedding 模型、向量库
- **待确认问题**：[列出需要用户拍板的技术决策]
````

**门禁**：A4 是**穿插式对齐**，不单独设门禁；其结论随 PRD 一并在「阶段 A 总确认」中由用户确认。

## A5：数据契约确认

PRD 初稿中所有**影响流程结果**的数据定义，必须以 checklist 形式列出，由 **Agent 完成梳理并逐项自检**。数据契约产出**不设用户门禁**（与 `SKILL.md` 全局规则一致），但必须完整、无遗漏。
**注意，整个项目的数据契约部分，不跟随V1或是V2变化，即使只是开发部分功能，数据契约也要完整设计**

### A5-1：业务数据契约

```markdown
### 数据契约确认清单

#### 商品分类体系
- [ ] 一级分类：服装、数码、食品、家居（共 4 类）
- [ ] 二级分类：服装-男装、服装-女装、数码-手机、数码-电脑...（共 15 类）

#### 用户画像字段
- [ ] 昵称（string）、注册时间（datetime）、会员等级（枚举：普通/白银/黄金）

#### 订单状态流转
- [ ] 状态：待支付 → 已支付 → 已发货 → 已签收 → 已完成

#### 权限角色
- [ ] 管理员：全部权限
- [ ] 普通用户：浏览、下单、查看订单
```

### A5-2：接口响应格式契约（必须在此阶段锁死）

```markdown
#### 统一响应格式
- [ ] 成功响应：`{"code": 200, "message": "success", "data": { ... }}`
- [ ] 错误响应：`{"code": <错误码>, "message": "<错误描述>", "data": null}`
- [ ] 分页响应：`{"code": 200, "data": {"items": [...], "total": 100, "page": 1, "page_size": 20}}`

#### HTTP 状态码约定
- [ ] 200：成功  /  400：参数错误  /  401：未认证
- [ ] 403：无权限  /  404：资源不存在  /  500：服务器内部错误
```

**规则**：业务数据契约和接口响应格式契约**不需要与用户确定**。梳理完成之后，**检验一遍**即可进入下个阶段

### A5-3：外部依赖与配置草稿（需用户确认）

前后端功能已经梳理完（A2 功能、A4 关键链路），此时 Agent **必须基于功能清单，自动推导出本项目所有需要外部配置 / 密钥 / 第三方依赖 / 账号 / 回调的点**，汇成一份「外部依赖与配置草稿」，交用户确认。这不限于 AI——**任何功能的外部配置都要进这份草稿**（AI 模型只是其中一类）。

> 与业务数据契约不同：本草稿**必须经用户确认**（涉及密钥、账号、付费、合规），是出 PRD 与进开发前的一道确认项。Agent 先出草稿，用户逐项确认或修改后锁定。允许填占位，但**不允许缺项**；凡功能链路里用到的外部依赖都必须出现在草稿里。未确认不得进入开发（见 router「开发门禁」）。

按项目实际列出，没有的类别显式写「无」：

```markdown
#### 外部依赖与配置草稿（草稿 → 待用户确认）

| 依赖 | 用途 | 关键配置字段 | Key/账号来源 | 存放位置 | 缺失时策略 | 状态 |
|------|------|-------------|-------------|----------|-----------|------|
| LLM（供应商/base_url/model） | … | `LLM_API_KEY` `LLM_BASE_URL` `LLM_MODEL` | 用户提供/平台内置/暂缺 | backend/.env | 真实/Mock | 待确认 |
| Embedding（供应商/model/维度） | … | `EMBEDDING_API_KEY` … | … | backend/.env | … | 待确认 |
| Rerank（供应商/model） | 链路含重排则必填 | `RERANKER_API_KEY` … | … | backend/.env | … | 待确认 |
| 第三方 API / 数据源 | … | … | … | … | … | 待确认 |
| 支付 / 结算 | … | … | … | … | … | 待确认 |
| 短信 / 邮件 / 推送 | … | … | … | … | … | 待确认 |
| 对象存储 / 文件服务（OSS/S3…） | … | … | … | … | … | 待确认 |
| 第三方登录 / SSO / OAuth | … | 回调地址、AppID/Secret | … | … | … | 待确认 |
| 微信小程序开放能力 | 登录 / 手机号 / 支付 / 订阅消息 / 分享 / 位置等 | `WECHAT_APP_ID` `WECHAT_APP_SECRET` `WECHAT_PAY_MCH_ID` `WECHAT_PAY_NOTIFY_URL` 等 | 用户提供/暂缺/Mock | backend/.env / 小程序公开配置 | Mock/fallback | 待确认 |
| 地图 / 定位 / 实名 / 风控 等 | … | … | … | … | … | 待确认 |
```

**生成规则**：逐个对照 A2 功能与 A4 关键链路，凡出现「调用外部服务 / 需要密钥账号 / 需要回调 / 涉及付费资源」的点，都必须落到草稿里一行。真实 Key / Secret 只进 `.env`，草稿与 PRD 只写字段名与配置状态。

**自检**：链路里用到的每个外部依赖（尤其 embedding 维度、rerank、支付回调）是否都在草稿里有明确行。出现「功能用了但草稿没写」即视为不完整。

## 落盘与 PRD.md 结构

**输出到**：`docs/PRD.md`（单一文件，持续迭代）

**PRD.md 阶段 A 建议结构**：

1. 背景与调研结论（阶段 R 选定方案的摘要）
2. 页面清单与跳转逻辑（A1）
3. 主要功能定义与分析，按页面组织（A2）

7. 外部依赖与配置草稿（A5-3，含每项配置状态与用户确认记录）
8. 微信小程序能力清单（仅 `target_platform=wechat-miniprogram` 项目）
