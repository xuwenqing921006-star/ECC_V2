# 阶段 B1：Design Spec

**在绘制原型前，必须生成轻量但可执行的 Design Spec。目标是让 B2 能快速出可看的前端原型，同时避免脱离竞品画面和业务需求。**

## 快速原则

- 调研不是目的：如果已有 `.sdd/tmp/visual-research.md` 或者 PRD，直接提炼，不重复搜索。
- 不做冗长设计文档：Design Spec 只写会影响原型绘制和后续前端实现的内容。
- 不新增多余门禁：B1 只发起一次确认，确认后 B2 直接进入原型制作。
- 缺少视觉上下文时可以继续，但必须明确使用默认设计基底：桌面 Web 用 Ant Design 风格，H5 页面用 Ant Design Mobile 风格。
- 如果界面清单包含手机浏览器 H5、微信内 H5 或 PWA，写 Design Spec 前必须读取 `harness-core/skills/sdd-h5-product-design/SKILL.md`，并把其中的 H5 页面设计规则写入 Design Spec。
- 如果界面清单包含原生微信小程序，写 Design Spec 前必须读取 `harness-core/skills/sdd-wechat-miniprogram-product-design/SKILL.md`，并把其中的小程序页面设计规则写入 Design Spec。

## 流程

1. 根据 `docs/PRD.md` 列出所有 MVP 界面清单。
2. **读取视觉调研上下文**
  如果 `.sdd/tmp/visual-research.md` 存在，必须读取并提取：
  - 用户选定的参考方向
  - 竞品截图 / URL / 页面视觉证据
  - 可借鉴的页面结构
  - 可借鉴的组件形态
  - 可借鉴的配色、字体、间距、圆角、信息密度
  - 明确不采用的竞品做法
   如果 `.sdd/tmp/visual-research.md` 不存在，不得阻塞全流程；必须在 Design Spec 中标注：
  - `visual_research_status: missing`
  - 默认设计基底
  - 需要用户后续补充的截图 / URL（如有）
3. **收集 Design Context**
  写 Design Spec 前，必须检查是否存在：
  - design system / UI kit / 组件库
  - 品牌规范 / Logo / 色彩 / 字体
  - 已有产品截图
  - 已有 codebase
  - 竞品截图或竞品 URL
   如果用户提供 codebase，必须优先读取 theme、tokens、global styles 和 2-3 个代表性组件，不得凭记忆重画。
4. **确定设计方向**
  - 如果阶段 R 已确认参考方向：沿用该方向，不再另起炉灶。
  - 如果需求清晰且已有视觉证据：确定 1 种视觉方向。
  - 如果需求模糊、视觉要求高、或缺少上下文：进入下方「设计方向顾问（轻量 fallback）」，给 3 个差异化方向让用户选择或混合；用户确认后再写 Design Spec。
5. **撰写 Design Spec**
  - 输出到：`<active_project_path>/.sdd/tmp/ui-design-spec.md`
  - 严格按下方「Design Spec 模板」撰写。Design Spec 是 B2 原型的唯一输入，必须能直接驱动画原型。
6. 发起确认：「Design Spec 已完成，请审阅。确认后进入阶段 B2 原型设计。」

**未经用户确认，不得进入阶段 B2。**

## 设计方向顾问（轻量 fallback）

仅在以下情况触发：阶段 R **未产出明确视觉方向**、需求模糊（如"做个好看的"）、或项目完全没有视觉上下文。如果 R 已定方向或用户已给明确参考，跳过本节，直接沿用。

给用户 **3 个差异化方向**，必须满足：

- 每个方向给**具体视觉特征**（配色倾向、字型气质、布局结构、信息密度），不能只给风格名（写「克制留白·单一暖色 accent·衬线标题」，不写「极简风」）。
- 3 个方向之间必须有**明显视觉反差**，避免三个都长得差不多。
- 每个方向一句话说明「适合谁/什么场景」。

用户选定或混合（如"A 的配色 + C 的布局"）后，再进入 step 5 撰写 Design Spec。不展开、不预生成原型——尊重用户节奏。
