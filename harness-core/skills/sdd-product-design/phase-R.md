## R0：需求澄清与用户对齐

阶段 R 的第一步不是直接做竞品调研，也不是直接沉淀视觉证据，而是先和用户完成一轮需求澄清，确保 Agent 与用户对项目理解处于同一状态。

如果用户没有清晰描述项目规划，必须先发起交流，不得直接进入竞品调研、视觉证据沉淀或后续 PRD 编写。

### 第一轮澄清目标

第一轮只向用户确认四个产品问题：

1. 这个系统要解决什么问题
2. 目标用户是谁
3. 用户在什么场景下使用
4. 系统大致包含哪些功能

不要在第一轮就追问版本规划、数据契约、AI 提示词、意图体系或复杂技术细节。第一轮目标是让用户用自然语言讲清楚产品方向。

### 提问方式

优先用一组简短问题让用户描述，不要一次性抛出长问卷。

开场模版：

```text
在进入竞品调研和 PRD 拆解前，我需要先确认我们对项目的理解一致。

请你先用自己的话描述一下：
1. 这个系统主要解决什么问题？
2. 目标用户是谁？
3. 用户会在什么场景下使用？
4. 这个系统大致需要包含哪些功能？
```

如果用户已经提供了部分信息，Agent 不要重复提问，应先总结已知信息，再只追问缺口：

```text
我先按当前信息理解为：
- 目标问题：
- 目标用户：
- 使用场景：
- 核心功能：

还缺这些关键信息：
1. ...
2. ...
```

### 功能拆解与 AI 识别

用户回答四个产品问题后，Agent 先在内部做一轮功能拆解，不需要把完整技术拆解过程反馈给用户确认。

拆解时先识别产品形态和已有技术事实，不预设技术栈：

- 已有项目：检测并继承受支持的语言、框架、组件库、接口和响应格式。
- 新项目：根据团队能力、交付目标、部署环境、成本和生态提出一个推荐技术栈及备选方案。
- 原生微信小程序：仅在用户确认后加载小程序专项规范。
- 技术选型属于后续架构决策；阶段 R 只补充会影响产品可行性的约束。

对每个用户提出的功能，判断：

1. 这是普通 CRUD / 页面交互 / 数据查询 / 业务流程，还是 AI 功能
2. 如果涉及 AI，AI 参与的是理解、分类、生成、召回、判断、推荐、总结、工具调用，还是 workflow 编排
3. AI 的输入来自用户输入、页面上下文、业务数据、知识库、文件、图片、语音，还是外部 API
4. AI 的输出是文本、结构化字段、推荐结果、报告、操作建议、工具调用参数，还是最终业务动作
5. 这个 AI 输出是否可以自动执行，还是必须用户确认
6. 如果涉及 LLM，确认模型/API 来源：用户自备 Key、平台内置模型、第三方服务，还是暂用默认占位配置

以上是 Agent 的**内部类型识别**，不必逐条反馈用户。但识别完类型后，必须进入下面的「功能 Pipeline 拆解」，把每个核心功能的产品节点和用户逐一对齐。

### 功能 Pipeline 拆解（逐节点与用户对齐）

**核心原则：一个功能 = 一条 pipeline。** 不要停留在「有这个功能」的粗粒度。识别功能类型后，必须把每个核心功能拆成从输入到最终产出的**节点链**，把关键节点的产品口径和用户对齐清楚。关键节点不得由 Agent 替用户拍板。

> **这不是门禁，更不是「每条 pipeline 一道确认」。** pipeline 拆解是 R0 需求澄清内部的一次梳理动作；整个 R0 只有**一道门禁**——最后的「需求对齐摘要」。不要输出「Pipeline 1/5…5/5」这种逐条卡用户确认的流程。

做法：

1. 对每个核心功能，画出它的 pipeline 节点链（输入 → … → 最终产出）。
2. 每个节点，对**关键且影响产品形态**的选择，带上推荐默认列出来（次要/纯技术节点直接给默认，不必问）。
3. **把所有核心功能的 pipeline 一次性整体呈现**（一张清单/几段即可），让用户一眼看全、集中回应；只在用户**真正分不清或有歧义**的少数节点上追问，不要逐条 pipeline 开轮次提问。
4. 用户对某节点没想法时，直接采用推荐默认并标注「默认，可改」，不阻塞、不卡确认。
5. 拆解出的节点口径，随「需求对齐摘要」一次确认，并承接到阶段 A 的功能定义与 A4 关键实现思路。

#### Few-shot 示例（按此粒度拆解，示例仅示范方法，不代表具体项目）

**示例 1 · 票据拍照自动录入（AI 功能）**

```text
pipeline：拍照/上传 → 图像预处理 → OCR 识别 → 字段结构化抽取 → 规则校验 → 异常人工确认 → 写入业务系统
```

逐节点对齐问题（每个都给推荐默认）：

- 输入方式：拍照 / 相册上传 / 批量上传 / 扫描件导入？单张还是多张？
- 票据类型：发票 / 收据 / 报销单 / 多类型混合？是否需要先分类？
- 识别字段：要抽取哪些字段（金额、日期、抬头、税号…）？哪些是必填？
- 校验规则：金额格式、日期合法性、与已有记录查重，命中后怎么处理？
- 识别不准的兜底：低置信度时转人工确认 / 高亮待核对 / 直接拒绝？
- 模型/服务来源：自建 OCR / 第三方 OCR API？（缺则写默认占位）

**示例 2 · 表格批量导入（普通业务功能也要拆 pipeline）**

```text
pipeline：上传文件 → 格式/编码校验 → 字段映射 → 行级校验 → 去重 → 入库 → 结果回执
```

逐节点对齐问题：

- 支持格式：仅 Excel 还是含 CSV？是否限制大小/行数？
- 字段映射：固定模板还是用户手动映射列？是否提供模板下载？
- 行级校验：必填项、类型、枚举值校验，单行报错是整批回滚还是跳过继续？
- 去重口径：按哪个字段判重？重复是覆盖 / 跳过 / 报错？
- 结果回执：成功/失败条数、失败明细是否可下载？

> 拆解任何功能时，都按上面这种「画出 pipeline → 列关键节点 → 带默认整体呈现，仅歧义处追问」的方式进行，让该功能的产品节点清晰即可。**所有 pipeline 一起呈现、随需求对齐摘要一次确认，不逐条卡门禁。示例只是演示拆解方法，实际拆解必须基于用户当前项目的真实功能。**

### AI 功能补充澄清

只有当某个功能涉及 AI 时，才向用户补问 AI 材料和智能边界。不要要求用户必须先准备好全部材料才能继续。

推荐问法：

```text
我判断这些功能里有 AI 参与：
- 功能 A：AI 负责 ...
- 功能 B：AI 负责 ...

请确认：你是否已经准备好这些 AI 材料？
1. 提示词或系统规则
2. 意图分类 / 任务分类体系
3. 示例输入输出
4. 知识库、业务数据或可检索资料
5. AI 可以自动执行的边界
6. 必须追问用户、拒绝或转人工的边界

另外，AI 的模型 / API 来源也请明确（这关系到后续能否真实联调）：
7. 模型供应商：百炼 / OpenAI / DeepSeek / 自建 / 其他
8. API Key 由谁提供：你提供测试 Key / 平台内置 / 暂无（先 Mock）
9. base_url 与 model 名称（如已知）
10. 若涉及 RAG：Embedding / Rerank 用哪家、是否同源

如果已经准备好，请提供材料。
如果还没有准备好，我会在 PRD 里写入默认占位配置，后续开发先按默认配置实现；但**模型 / API 来源在进入开发前必须明确**，否则只能按 Mock/降级开发，无法真实联调。
```

处理规则：

- 用户提供 AI 材料：把材料整理进需求对齐摘要；阶段 A 写 PRD 时必须承接到 AI 功能章节，包括提示词、意图体系、输入输出、边界和默认行为。
- 用户没有准备 AI 材料：不得阻塞流程；必须提前声明将由 Agent 按当前需求和默认工程判断生成默认配置，阶段 A 写入 PRD。用户后续可以在 PRD 中修改默认配置。
- 用户说不需要 AI：把相关功能按普通业务流程处理，不写 AI 章节。
- 如果 AI 功能涉及高风险自动执行，必须默认加入用户确认门禁，不得默认自动执行。
- 如果用户无法继续澄清某个 AI 边界或材料，必须明确告知：

```text
这部分信息当前还不完整。为了不阻塞后续流程，我会先基于 AI 的自主决策生成默认配置，并在 PRD 中明确标注为“默认配置，可修改”。后续你可以在 PRD 中调整提示词、意图体系、知识来源和智能边界。
```

AI 默认配置必须包含以下结构，供阶段 A 写入 PRD：

```text
AI 默认配置
- AI 参与功能：
- 模型 / API 来源：供应商 / Key 来源 / base_url / model（未定则标注「待用户确认，开发前必须明确」）
- 默认意图分类：
- 默认提示词方向：
- 默认知识来源：
- Embedding / Rerank 来源（如涉及 RAG）：
- 默认输出格式：
- 默认自动执行边界：
- 必须用户确认的场景：
- 必须追问 / 拒绝 / 转人工的场景：
- 后续可替换项：
```

### 对齐输出

完成交流后，先在对话中输出一版“需求对齐摘要”，让用户确认：

```text
需求对齐摘要
- 项目目标：
- 目标用户：
- 使用场景：
- 核心问题：
- 核心功能：
- 功能 Pipeline 关键节点口径：逐个核心功能列出 pipeline 节点链 + 各节点已确认/采用默认的口径
- AI 功能判断：无 / 有，涉及哪些功能
- AI 模型/API 来源：供应商 / Key 来源 / base_url / model（未定则标注「待确认，开发前必须明确」）
- AI 材料状态：已提供 / 未提供，使用默认配置
- 智能边界：可自动执行 / 必须用户确认 / 必须追问 / 必须拒绝或转人工
```

用户确认这份摘要后，才允许进入 R 阶段竞品调研与视觉证据沉淀。

### 写入规则

- 本步骤默认先在对话中完成，不必单独创建新文件。
- 如果用户输入很长、分支很多、业务口径不稳定，转入 `harness-core/skills/alignment/SKILL.md`，产出 `<active_project_path>/docs/澄清文档/<feature-name>/01-alignment.md` 后再回到阶段 R。
- 用户确认后的需求对齐摘要，应在阶段 A 合并进入 `<active_project_path>/docs/PRD.md` 的背景、目标用户、问题定义、核心功能等章节。
- 如果存在 AI 功能，阶段 A 必须在 `<active_project_path>/docs/PRD.md` 中新增或补充 AI 功能章节，写清楚 AI 参与位置、提示词/意图体系材料状态、默认配置、智能边界和后续待替换项。

**未经用户确认需求对齐摘要，不得进入 R 阶段竞品调研与视觉证据沉淀。**

## R1：竞品调研执行

充分理解后，调研同类竞品（至少 2 个，至少 1 个国内产品）。调研必须同时覆盖「产品结论」和「视觉证据」。

如果项目属于内部工具、极小众或全新场景，确实找不到 2 个可比竞品，必须在对话中说明原因，并改为：调研相邻领域的参考产品或交互范式（至少 1 个），不得因缺少直接竞品而跳过本步骤。

每个竞品必须记录：

- 产品名称与 URL
- 目标用户与核心场景
- 关键流程
- 核心交互
- 页面结构
- 视觉风格
- 组件形态（导航、卡片、表单、列表、详情页、CTA 等）
- 可借鉴点
- 不采用点
- 视觉证据：截图路径 / 截图文件名 / 用户提供图片 / 可访问 URL

如能访问公开页面，优先用浏览器或 Playwright 截图。无法截图时必须说明原因，并要求用户提供截图，或让用户明确允许只基于文字调研继续。

## R2：调研产出与视觉证据落盘

调研结论和参考方案先在对话中呈现，让用户选择 A/B/C 或融合方案。

用户确认参考方向后，如果本轮存在可复用视觉证据，写入：

```text
<active_project_path>/.sdd/tmp/visual-research.md
```

`<active_project_path>/.sdd/tmp/visual-research.md` 至少包含：

```markdown
# Visual Research

## 竞品视觉证据表
| 竞品 | URL | 截图/证据路径 | 可借鉴点 | 不采用点 |
|------|-----|---------------|----------|----------|

## 用户选定方向
- 采用：A / B / C / 融合
- 选择原因：

## 可复用视觉规则
- 页面结构：
- 组件形态：
- 色彩倾向：
- 字体/字号倾向：
- 间距/圆角/阴影：
- 信息密度：

## 原型阶段必须参考
- [截图或 URL 1]：用于参考 [页面/组件/交互]
- [截图或 URL 2]：用于参考 [页面/组件/交互]

## 禁止照搬
- 不复制竞品品牌、Logo、真实文案、商业数据
```

如果本轮没有可用视觉证据，不强制创建 `visual-research.md`。必须在对话中说明原因，B1 将改用用户截图、品牌资料、已有代码或默认设计基底继续。

关键产品结论写入后续 `<active_project_path>/docs/PRD.md` 背景章节；如生成视觉证据文件，保留到 B2 原型完成后再清理。

如果前置场景对齐稿存在，阶段 R 的调研结论必须继承其业务目标、范围和验收口径，不得自行扩大功能范围。

## 阶段 R 门禁

向用户发起确认：

```text
请确认阶段 R 结果（需求对齐摘要已在 R0 确认，此处不再重复）：
1. 竞品参考方向采用 A/B/C 还是融合方案？
2. 如果存在 AI 功能，是否接受当前 AI 默认配置进入 PRD？

确认后进入阶段 A。
```

**未确认不得进入阶段 A。**
